## 0. 方案总览

### 0.1 分级与处置策略

| 等级 | 判定标准 | 数量 | 本轮处置 |
|---|---|---|---|
| **高** | 可导致权限绕过/凭据泄露/接管服务器/数据损坏/发布不可回退 | 9 项（报告 #1–#9） | **全部实施**，上线前必须闭环 |
| **中** | 可导致信息泄露/注入面/认证弱化，需攻击者具备一定条件 | 5 项（报告 #10–#14） | **实施**（成本可控，随高项同批或后续窗口） |
| **低** | 工程质量/可维护性/测试覆盖/监控缺失，非直接安全漏洞 | 9 项（报告 #15–#23） | 本轮**不实施**，转入 R2 迭代；其中 2 项"搭车项"低成本顺带完成 |

> 说明：报告核心卡片标注"严重 5 / 高危 4 / 中低 14"，与第 2 节明细表（🔴5 / 🟠4 / 🟡14，共 23 项）、第 3 节行动清单（P0×3 / P1×6 / P2×8，共 17 条）三处计数口径不一致。本方案以**明细表 23 项**为全集，以**行动清单的紧急度**排序实施，并在第 1 节逐项标注两种口径，避免遗漏。

### 0.2 三条不可妥协的约束

1. **#2（关闭 18090 明文端口）是"条件收口"而非"立即关停"**：其前置条件是全部在册终端完成 TLS 迁移。终端未 100% 就绪前，只允许"收紧"（防火墙限源），不允许"关闭"，否则终端心跳与管理通道整体中断。
2. **#1（删除白名单）改造不得扩大删除能力，只收窄**：改造后的删除能力必须是改造前的子集，且正常"扫描→勾选→删除"主流程零感知。
3. **#8（SQLite 加锁）必须先压测后上线**：全局串行化有吞吐劣化风险，需在预发环境以真实并发量验证 P95 无显著劣化后再合入。

## 2. 逐项改造措施

### H1 · 删除白名单逃逸（P0）

**现状**：`_EXTRA_ALLOWED_ROOTS` 为模块级全局 `set()`，扫描过程中在 733（自定义根）、748（浏览器下载目录）、807（全盘模式逐文件父目录）三处 `add()`，无任何清理；`_is_delete_allowed()`（565）以该集合做前缀放行。经多轮扫描或 alldisks 模式后，集合膨胀至覆盖大量目录，删除接口（568 `handle_appdata_delete`）据此放行——扫描的副作用变成了删除授权。

**改造方案**：
1. **授权与扫描解耦，改为"结果集 + 会话作用域"校验**
   - 新增 `_DeleteTicket` 结构：`{scan_id, expires_at, allowed_paths:set}`，随扫描任务创建，TTL 默认 30 分钟，任务完成/超时/进程重启即失效。
   - 删除接口改为必带 `scan_id`（或 task_id），校验：**待删路径的规范化 realpath 必须 ∈ 该 scan_id 实际返回过的 items 路径集合**（精确匹配，非目录前缀）。
   - `_EXTRA_ALLOWED_ROOTS` 全局集合**删除**；若短期内需兼容旧前端，保留为只读空集合并在 alldisks 模式下禁止写入。
2. **路径规范化加固**：统一 `_norm()` + `os.path.realpath()`，拒绝含 `..`、UNC、符号链接逃逸的目标；删除前二次 realpath 复检。
3. **双副本同步**：`disk-cleaner/appdata_scan.py` 与顶层 `appdata_scan.py` 同改，改后核对两份文件 MD5 一致（ADR-011 同步契约）。

**技术实现要点**：不引入新依赖；TTL 集合放在模块级 dict + 惰性清理（每次删除请求触发过期扫描），避免常驻线程。

**业务影响与兜底**：
- 影响面：仅"扫描后长时间未操作再删除"的场景需重新扫描（前端提示"结果已过期，请重新扫描"）。正常"扫描→勾选→删除"零感知。
- 兜底：TTL 设为 30 分钟（远大于正常操作耗时）；前端删除前若 ticket 失效，返回明确错误码 `scan_expired`，UI 引导重扫而非静默失败。

**验收标准**：单测 4 类必过——①跨 scan_id 不可删 ②未在结果集中的路径不可删 ③TTL 过期不可删 ④正常流程可删；并补**破坏性删除 fail-closed 单测**（报告 #20 提升项）：非法/越界路径一律拒绝且不产生任何文件系统副作用。E2E 断言删除主流程仍可用。

### H2 · legacy HTTP 18090 明文端口（P0，条件收口）

**现状**：生产三监听并行——18090 明文（scope=all 全路由）、18443 TLS 终端口、**443** TLS 管理口（2026-09 由 8443 迁移；`deploy/terminal-platform.service` 已补 `AmbientCapabilities=CAP_NET_BIND_SERVICE`，commit `431166c`）；deploy.py 幂等迁移补 `legacy_http.enabled=true`（325），防火墙持久放行 18090。

**判定限制（阶段 0 实测）**：服务端无法自证终端走 http 还是 https——`terminals` 表不存 uplink 地址，`server_url` 仅存在于定制包文件名协议。就绪度必须从**流量侧**取得（防火墙包计数增量 / 连接态采样），或直接用"软收口"实测（步骤 3）。

**改造方案（三步，不可跳步）**：
1. **盘点（阻断前置）**：从服务端 `terminals` 表导出清单，字段含 `client_version`、`uplink_config.server_url`、`last_seen`，输出三类：A 已走 https:18443 / B 有能力未切换 / C 无 TLS 能力（版本过低，如已挂起的 4.0.0 终端）。
2. **逐台灰度切换**：对 B 类经命令通道下发 `uplink_config`（`server_url=https://172.17.5.215:18443` + `server_ca_fingerprint`），逐台观察 `last_seen` 连续 ≥2 个心跳周期且 18443 心跳 200；**任一台失败立即回改 http://（秒级生效）**。C 类先升级客户端至 ≥4.1.8 再纳入灰度。
3. **收口（优先"软收口"）**：全部在册终端稳定 ≥24 小时后，**先在防火墙 DROP 18090**（服务保持监听，可秒级恢复）→ 观察 24h 掉线情况 → 确认无终端掉线后再执行 `legacy_http.enabled=false` → 移除 firewalld 18090 条目（runtime + permanent 双重复核）→ 重启 → 健康检查（18090/18443/443 三端口、TLS health、跨类 404）。
   - 软收口优于直接关服务：能直接暴露"是否仍有终端走明文"，且回退只需删一条防火墙规则，无需重启服务。
4. **端口口径统一**：代码默认值仍为 8443（`app.py:39/242`、`deploy.py:316`、`test_https_split.py:100`），与生产 443 不一致——全新环境部署将得到 8443，运维口径分裂。本轮将默认值统一为 443，并同步测试断言与文档；同时核对**部署模板 unit 与生产 unit 一致**（431166c 是"远端 sed + 模板固化"两处，须验证生产实际生效，避免只改远端/只改模板的单边状态）。
5. **443 能力依赖**：管理口 443 属特权端口，服务以 `eyeterm` 非 root 运行，unit 必须声明 `AmbientCapabilities=CAP_NET_BIND_SERVICE`；缺失时表现是"重启后 bind 443 errno13 崩溃、旧进程存活"，极易误判为网络问题。收口与后续任何重启前，均需核对 unit 声明。

**回退开关**：`legacy_http.enabled=true` + 防火墙复原，秒级；runbook 中固化命令序列。

**未就绪时的处置（重要）**：若阶段 2 结束时仍有终端未切换，则 18090 维持开启，但**收紧为仅放行终端网段与管理端网段**（`firewalld --add-rich-rule` 限源），作为遗留风险上报决策人，不得强行关闭。

**验收标准**：全部终端 18443 心跳连续 24h 无掉线；`ss -lntp` 无 18090 监听；`firewall-cmd --list-all` 无 18090；`curl --cacert` 验证 TLS health 200（终端 18443 与**管理 443** 两口均验）；跨类访问 404 断言成立；管理端入口 `https://<host>:443/` 页面与登录正常；`systemctl cat terminal-platform | grep AmbientCapabilities` 含 `CAP_NET_BIND_SERVICE`。

### H3 · SSH 主机密钥不校验（P0，范围已扩大）

**现状**：`deploy/deploy.py:98`；**新增发现**：生产模块 `server/deep_engine.py:93`；运维工具 `tools/ssh_run.py:39`；另有十余个 `tools/_*.py` 临时脚本。

**改造方案**：
1. **公共连接函数收口**：在 `tools/ssh_run.py` 中提供统一 `connect(host, port, user, password, expected_fp=None)`，策略用 `paramiko.RejectPolicy()`，连接前/后比对 `client.get_transport().get_remote_server_key().get_fingerprint()`（SHA256），与 `ETP_SSH_HOST_FINGERPRINT`（hex 或 base64）或 `known_hosts` 白名单不一致即抛错终止。
2. **生产代码改造**：`deploy/deploy.py:98` 与 `server/deep_engine.py:93` 均改用该函数；deep_engine 的指纹来源复用 settings/config 中的可信指纹项（缺失时 fail-closed，不回退 AutoAdd）。
3. **一次性指纹登记**：首次部署前由管理员在受控网络下采集并登记服务器主机指纹，写入运维凭据库（不入仓库）。
4. **临时脚本**：`tools/_*.py` 中带 AutoAddPolicy 的脚本统一纳入**临时文件统一清理批次**；确需保留的改调公共函数。

**业务影响与兜底**：服务器重装或 sshd 密钥轮换后，部署/采集会因指纹不匹配而失败——这是预期行为（正是防 MITM 的目的）。runbook 必须写明"密钥变更流程：先在受控网络重新采集指纹 → 更新 ETP_SSH_HOST_FINGERPRINT → 再部署"。

**验收标准**：单测——正确指纹连接成功、错误指纹必抛错且不建立连接；真实部署演练一次（指纹正确）；grep 门禁：生产代码中 `AutoAddPolicy` 零命中。

### H6 · storage.py shell=True 命令注入

### H8 · SQLite 并发访问不安全

**现状**：`store.py:306` 单连接 `check_same_thread=False`，`:304` 已有 `self._lock` 但仅覆盖部分写路径，读路径未持锁 → 并发下 `database is locked`、游标复用损坏。

**改造方案（两步走）**：
1. **第一步（本轮）**：把所有连接访问（含全部读方法）纳入 `with self._lock:`，保持 WAL + `timeout=30`；以装饰器或统一 `_with_conn()` 上下文收口，避免逐方法遗漏。
2. **第二步（条件触发）**：若压测显示吞吐劣化不可接受，再改每请求独立连接（thread-local 或上下文内 `sqlite3.connect`），本轮仅做预案不实施。
3. 增加并发一致性单测：多线程并发读写同一表，断言无异常、无脏读。

**业务影响与兜底**：全局锁会串行化数据库操作，存在吞吐下降风险。**必须先在预发以真实并发量压测**（模拟心跳上报 + 控制台查询并发），P95 相对基线劣化 < 10% 方可上线；否则回退到第二步方案。生产已有数据不受影响（仅并发访问方式变化）。

**验收**：并发压测无 `database is locked`；既有多套 E2E/冒烟在加锁后全绿；吞吐对比报告留档。

### H9 · 并发清理请求静默丢弃

**现状**：`disk_cleanup.py:1018-1030`，已有 job 运行时新请求返回旧 job_id 并忽略新 categories，用户侧无感知。

**改造方案**：改为**显式拒绝 + 状态透出**：检测到活跃 job 时返回 `{"ok": false, "reused": true, "job_id": <活跃ID>, "running_categories": [...]}`，HTTP 语义用 409；前端据此提示"已有清理任务进行中（分类：…），请等待完成或取消后再发起"。R2 再考虑引入排队队列。

**验收**：单测断言并发请求返回 reused 且 categories 不被静默丢弃；前端提示可达（E2E 或手工）。

| L2 单测 | 逐项新增/扩展单测 | H1 四类 + 破坏性删除 fail-closed；H3 指纹正反例；H6 注入被拒；H8 并发一致性；H9 reused；H4 CA 正反例 | H1、H3、H4、H6、H8、H9 |
| L3 集成冒烟 | `tools/smoke.py`（基线 55/55，含 HTTPS 分离组 7 项）+ 后端冒烟 | 全绿且 HTTPS 组不受扰 | H2、H6、H8 |
| L4 前端 E2E | `e2e_console`（基线 206/206）、`e2e_home`、`e2e_perf`、`e2e_loginspector`、`e2e_disk`、netdoctor E2E（94/94） | 全绿 + `pageerror=0` | M4（CSP 不阻断页面）、M3、H9 |
| L5 预发压测 | 并发脚本（心跳 + 控制台查询） | 无 `database is locked`；P95 劣化 < 10% | H8 |
| L6 生产验收 | 真实终端心跳、管理端登录、关键业务功能清单（见 5.3） | 连续 24h 稳定 | H2、H8 |

### 5.2 改造前后基线对比（防止"修好安全、弄坏功能"）

每项改造合入前记录基线 → 合入后复跑 → 对比项必须"全绿且不劣化"。当前已知基线：`e2e_console` 206/206、`smoke.py` 55/55、`test_vlan_kb` 27/27、`test_wol` 15/15、`test_https_split` 27/27、netdoctor E2E 94/94、loginspector E2E 43/43。

### 5.3 业务功能回归清单（每阶段出口必须复验）

| 业务 | 复验方式 |
|---|---|
| 终端心跳 / 注册 / 命令通道 | 真实终端 last_seen 连续 + 18443 心跳 200 |
| AI 智能分析 | 控制台发起一次分析，返回成功（网关正常时） |

| 日志检索与 txt 导出 | 导出成功、编码正确 |
| 性能分析与报告导出（HTML） | 导出文件可打开 |
| 网络排障（连通性/路由/压测） | 连通性跑通；iperf 需服务器配合 |

### 5.4 测试载荷纪律（沿用既有事故教训）

注入类测试**禁止使用真实攻击串**（如 `rm -rf`），一律使用良性化载荷（`; echo injected`、`$(echo x)`）；冒烟脚本**禁止触碰生产 `llm.*` 配置**，用隔离键测试并测后恢复。

## 6. 复查与持续监控机制

### 6.1 防复发门禁（提交前必跑）

`tools/gate_all.py` 聚合：py_compile → 安全禁项扫描（L1）→ 受影响模块单测 → 受影响 E2E。任何一项红即禁止合入。将"禁 shell=True / 禁 AutoAddPolicy / 禁硬编码凭据 / 禁全局可变删除白名单 / SQLite 访问必须持锁"写入新增代码红线，在代码评审清单中逐条勾核。

### 6.2 周期性复查

| 周期 | 内容 | 责任人 |
|---|---|---|
| 每次发布前 | 门禁全跑 + 回归清单 + 回滚演练 | 质量门神（main 代行） |
| 每周 | 禁项扫描复跑；证书剩余天数检查（复用已有 `cert_not_after()`） | server-platform-dev |
| 每月 | 凭据轮换检查（terminal_token、console 口令、FTP、交换机只读账号）；依赖与端口暴露面复核 | main + 用户 |
| 每季度 | 完整安全基线复检（对齐本报告 23 项），输出复检报告 | 全体 |

### 6.3 运行期监控（务实轻量方案，替代重型引入）

- 证书过期：扩展 health 端点暴露证书剩余天数，<30 天告警（已有解析函数可复用）。
- 服务存活与重启：补 systemd `MemoryMax` / `StartLimitIntervalSec`（搭车项 #22），避免重启风暴。
- 关键指标：端口监听状态、health 200、终端 last_seen 掉线数、数据库锁错误日志关键字（改造后应为 0）纳入日常巡检。
- 日志：部署日志脱敏（M1）后，仍禁止将含凭据的日志外发或入仓。

### 6.4 文档与台账收口

改造完成后：`docs/` 增补 runbook 与复检报告；新增/变更端点同步登记至 `docs/API-REGISTRY.md`（api-registrar-dev）；ADR 与编年史归档（archivist-dev / chronicler-dev），确保下次复检可追溯。

## 7. 风险与回滚预案

| 改造项 | 主要风险 | 触发信号 | 回滚动作 | 恢复时限 |
|---|---|---|---|---|
| H1 白名单 | 正常删除被误拦 | 用户反馈删除失败 | 回退 appdata_scan.py 上一版并重建 exe | 分钟级（需 exe 重建则小时级） |
| H2 关 18090 | 终端失联 | last_seen 掉线、18443 心跳失败 | `legacy_http.enabled=true` + 防火墙复原 | 秒级 |
| H3 SSH 指纹 | 服务器重装/密钥轮换后部署失败 | 连接报指纹不匹配 | 受控网络重采指纹并更新（**不得**改回 AutoAdd） | 分钟级 |
| H6 storage | 合法挂载配置被误拒 | SMB/存储功能异常 | 回退 storage.py 上一版；已保存的非法值按快照恢复 | 分钟级 |
| H7 口令 | 部署缺变量而中止 | 部署报 missing env | 提供环境变量后重跑 | 分钟级 |
| H8 SQLite 加锁 | 吞吐劣化 | 压测 P95 劣化 ≥10% | 回退加锁，改用每请求独立连接预案 | 分钟级 |
| H9 并发清理 | 前端未适配 409 导致用户困惑 | 前端提示缺失 | 前端兼容提示（服务端语义保留） | 分钟级 |
| M4 CSP | 页面样式/脚本被阻断 | E2E 转红或 pageerror | 该页 CSP 回退（分页独立） | 分钟级 |

**通用兜底**：所有生产变更前备份（config.json、服务端代码、data 目录），备份路径打印并留档；任一阶段出口未达标即停止后续阶段，不带着未闭环的高危项进入下一阶段。
