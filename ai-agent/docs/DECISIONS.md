# AI Agent 架构系统 · 决策记录（ADR）

> 架构层面的重要取舍必须追加条目。格式：背景 → 决策 → 理由 → 影响。
> 小的实现细节不必记录；凡"换一种做法也能跑，但选择这一种有明确依据"的，记下来。

## ADR-001 · 记忆按「模块」物理隔离，跨模块引用需显式声明

**日期**：2026-09-19　**状态**：已采纳

**背景**
项目 AI 能力会持续增多（现有四套：智能分析 / 智能诊断 / IP 冲突 / 资产定位），
若所有模块共享一份记忆，必然出现**语义串扰**——诊断模块的故障结论被分析模块
当成该终端的固有属性引用，越用越偏。

**决策**
- 记忆目录按 `module_id` 一模块一个：`memory/<module_id>/`
- 一切读写经 `MemoryScope(module_id)` 收口，**禁止跨目录直接 open()**
- 记忆条目带 `module` 字段；跨模块引用必须显式声明 `depends_on`

**理由**
物理隔离是最硬的一道闸——代码层面根本"顺手读隔壁"读不到。命名空间标注则让
**合法共享**（如诊断需要分析模块的历史结论）与**意外串扰**可区分、可审计。

**影响**
- 每个新模块接入需建自己的记忆目录（接入成本极低，隔离收益长期）
- 需要跨模块信息时走显式声明，多写一行元数据，换来可追溯

## ADR-002 · 声明与状态分离（人读的 / 机写的分开存放）

**日期**：2026-09-19　**状态**：已采纳

**背景**
参考 CodeBuddy（agent 定义在 md、automation 运行时机状态在 SQLite）、
Codex（`~/.codex/` 下配置与 sessions 分置）的形态，二者都把**声明**与**状态**分开。

**决策**
- **声明类**（人读、可版本化、变更需评审）：`SOUL.md`、`SKILL.md`、`MEMORY.md`
- **状态类**（机器写、可重建、频繁变动）：`STATE.json`、`SESSION.jsonl`、`archive/`

**理由**
两类数据的**变更频率、变更者、可靠性要求**完全不同。混在一起会导致：
自动流程意外改写人工审定的声明；或人工编辑时误伤机器状态。

**影响**
- `MEMORY.md` **只增不改** —— 修正结论靠追加新条目，历史可回溯
- `STATE.json` 可覆盖写（它只是当前进度指针，丢了可从 SESSION 重建）

## ADR-003 · 会话增量用 JSONL 追加，不用单文件重写

**日期**：2026-09-19　**状态**：已采纳

**背景**
Codex 的 sessions 目录采用**每会话一个 JSONL、逐行追加**的形态。

**决策**
`SESSION.jsonl` 逐行追加（append-only），崩溃最多丢尾行；超阈值时**整段轮转**
到 `archive/`，不截断、不重写。

**理由**
- **崩溃安全**：重写式存储在中途崩溃会毁掉整个文件；追加式最坏丢最后一行
- **可回放**：逐条记录推理过程，事后能回答"它当时凭什么这么判断"
- **轮转不丢历史**：归档段保留，只是不参与日常读取

**影响**
- 单文件会增长 → 必须配套轮转（已实现于 `tools/cleanup.py`）
- active 段默认不轮转（正在被写），需 `--include-active` 显式开启

## ADR-004 · 一键清理默认 dry-run

**日期**：2026-09-19　**状态**：已采纳

**背景**
用户要求"防止临时文件无限累积，提供一键清理"。但清理**不可逆**，而这类工具
一旦默认执行，误删（尤其是 SOUL/SKILL/MEMORY 这类不可重建的声明文件）代价极高。

**决策**
- `cleanup.py` **默认 dry-run**，真删需显式 `--apply`
- 治理范围**限定三处**：`tmp/`（按 TTL）、`memory/*/SESSION.jsonl`（超阈值轮转）、
  `memory/*/archive/`（超保留期 purge）
- **硬保护**：`SOUL.md`、`skills/**`、`MEMORY.md`、`STATE.json` 永不触碰
- 路径 `resolve()` 后校验必须位于 `ai-agent/` 之下（防符号链接逃逸）
- 轮转用 `os.replace()` 同盘原子移动，不丢数据

**理由**
"一键"的诉求是**省事**，不是**放手**。dry-run 默认 + 范围硬限定 + 保护名单，
三者叠加才能在"好用"与"不会出事"之间站住。

**影响**
- 自动化定时清理需显式带 `--apply`
- 新增受治理目录时必须同步更新保护名单与范围校验

## ADR-005 · 只有 tmp/ 允许自动清理，主仓根禁止散落临时文件

**日期**：2026-09-19　**状态**：已采纳

**背景**
实测主仓根已堆积 **60+ 个** `_xxx.txt` / `_xxx.py` 临时文件（探针、构建日志、
一次性脚本），来源是历次开发中"随手写在根目录"。它们既无法判断是否过期，
也不敢贸然清理——**没有约定的临时区，就没有安全的清理边界**。

**决策**
- 一切中间产物**必须**落 `ai-agent/tmp/`（带 TTL，可被清理工具无条件清扫）
- 各业务模块若需临时文件，用各自模块的 tmp 子目录（如 `perf-analyzer/tmp/`），
  并纳入清理工具的治理范围
- **禁止**在项目根创建 `_xxx` 形式的散落文件

**理由**
"能不能自动清理"取决于"是否知道它是什么、属于谁、何时过期"。有约定的临时区
才有元数据，有元数据才敢清理。

**影响**
- 探针脚本改为落在模块 tmp 下，且**用完即删**（不留到下一轮）
- 存量散落文件需一次性归置（清理或归档），由 main 决定时机

## ADR-006 · AI 环节必须有硬预算，超时降级不阻断主链

**日期**：2026-09-19　**状态**：已采纳（事故沉淀）

**背景**
2026-09-19 实测：**资产定位**功能在控制台报「定位超时」。排查链路——
- LLM 模型链 `timeout=45s` × 2 模型 = 最坏 90s
- 画方（nad）准入检索：1588 台终端需翻 2 页，单请求超时 10s → 最坏 20s
- 二者叠加（且服务是**单线程**，慢请求阻塞全局）→ 逼近前端 25s 兜底
- 结果：**用户连平台/火绒的确定数据都看不到**（AI 只是三源之一，却拖垮了整条聚合）

**决策**
1. 任何 LLM 调用的 `timeout` 与模型链长度**必须**计入预算，最坏耗时 ≤ 场景预算
2. 任何外部检索（第三方 API、跨网段请求）**必须**加**线程预算**收口
   （`_search_nad` 用 `threading + join(budget)` 硬收口）
3. AI 失败/超时一律**降级为 `available=false` + 原因**，确定数据照常返回
4. 交互式（P0）场景：**硬预算优先于完整度**

**理由**
AI 是**增益项**。让增益项阻断主链，是设计缺陷而非 AI 能力不足。
用户要的是"能看到确定数据 + 有 AI 补充更好"，不是"AI 不出来就什么都没有"。

**影响**
- 新增 AI 能力需在 `SKILL.md` 标注触发类型与预算等级
- 预算参数集中可配，便于按实测收紧（本次：LLM 8s/模型、画方 4s/请求 + 8s 线程预算）

## ADR-007 · 缓存/记忆写入失败时保留旧值，不写空

**日期**：2026-09-19　**状态**：已采纳（事故沉淀）

**背景**
同一次排查中发现：画方缓存 `nad_terminals_cached()` 在拉取失败时**写空缓存**
（`terms=None` + `ts=now`）。后果是——一次网络抖动 → 其后 5 分钟（TTL）内
**所有**读路径都拿不到画方数据，且不会重试。雪上加霜。

**决策**
- 拉取失败且**已有可用旧值** → **保留旧值**继续服务（按旧值服务优于无数据）
- 仅当**从未有过好数据**时才记录失败原因
- 同理适用于记忆写入：Skill 校验失败 → 拒绝写入，**不改动既有条目**

**理由**
"旧但可用"与"新但空"之间，前者对使用者价值更高。失败语义不该惩罚已有数据。

**影响**
- 缓存实现需区分"无数据"与"有旧数据但刷新失败"两种状态
- 需要配套的**数据新鲜度标注**（旧值要能让使用方知道它旧了）
