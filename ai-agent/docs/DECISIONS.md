> 小的实现细节不必记录；凡"换一种做法也能跑，但选择这一种有明确依据"的，记下来。

## ADR-001 · 记忆按「模块」物理隔离，跨模块引用需显式声明

**日期**：2026-09-19　**状态**：已采纳

**背景**
项目 AI 能力会持续增多（现有四套：智能分析 / 智能诊断 / IP 冲突 / 资产定位），
若所有模块共享一份记忆，必然出现**语义串扰**——诊断模块的故障结论被分析模块
当成该终端的固有属性引用，越用越偏。

**决策**
- 记忆目录按 `module_id` 一模块一个：`memory/<module_id>/`
- 一切读写经 `MemoryScope(module_id)` 收口，**禁止跨目录直接 open()**
- 记忆条目带 `module` 字段；跨模块引用必须显式声明 `depends_on`

**理由**
物理隔离是最硬的一道闸——代码层面根本"顺手读隔壁"读不到。命名空间标注则让
**合法共享**（如诊断需要分析模块的历史结论）与**意外串扰**可区分、可审计。

**影响**
- 每个新模块接入需建自己的记忆目录（接入成本极低，隔离收益长期）
- 需要跨模块信息时走显式声明，多写一行元数据，换来可追溯

## ADR-002 · 声明与状态分离（人读的 / 机写的分开存放）

**日期**：2026-09-19　**状态**：已采纳

**背景**
参考 CodeBuddy（agent 定义在 md、automation 运行时机状态在 SQLite）、
Codex（`~/.codex/` 下配置与 sessions 分置）的形态，二者都把**声明**与**状态**分开。

**决策**
- **声明类**（人读、可版本化、变更需评审）：`SOUL.md`、`SKILL.md`、`MEMORY.md`
- **状态类**（机器写、可重建、频繁变动）：`STATE.json`、`SESSION.jsonl`、`archive/`

**理由**
两类数据的**变更频率、变更者、可靠性要求**完全不同。混在一起会导致：
自动流程意外改写人工审定的声明；或人工编辑时误伤机器状态。

**影响**
- `MEMORY.md` **只增不改** —— 修正结论靠追加新条目，历史可回溯
- `STATE.json` 可覆盖写（它只是当前进度指针，丢了可从 SESSION 重建）

## ADR-003 · 会话增量用 JSONL 追加，不用单文件重写

**日期**：2026-09-19　**状态**：已采纳

**背景**
Codex 的 sessions 目录采用**每会话一个 JSONL、逐行追加**的形态。

**决策**
`SESSION.jsonl` 逐行追加（append-only），崩溃最多丢尾行；超阈值时**整段轮转**
到 `archive/`，不截断、不重写。

**理由**
- **崩溃安全**：重写式存储在中途崩溃会毁掉整个文件；追加式最坏丢最后一行
- **可回放**：逐条记录推理过程，事后能回答"它当时凭什么这么判断"
- **轮转不丢历史**：归档段保留，只是不参与日常读取

**影响**
- 单文件会增长 → 必须配套轮转（已实现于 `tools/cleanup.py`）
- active 段默认不轮转（正在被写），需 `--include-active` 显式开启

## ADR-004 · 一键清理默认 dry-run

**日期**：2026-09-19　**状态**：已采纳

**背景**
用户要求"防止临时文件无限累积，提供一键清理"。但清理**不可逆**，而这类工具
一旦默认执行，误删（尤其是 SOUL/SKILL/MEMORY 这类不可重建的声明文件）代价极高。

**决策**
- `cleanup.py` **默认 dry-run**，真删需显式 `--apply`
- 治理范围**限定三处**：`tmp/`（按 TTL）、`memory/*/SESSION.jsonl`（超阈值轮转）、
  `memory/*/archive/`（超保留期 purge）
- **硬保护**：`SOUL.md`、`skills/**`、`MEMORY.md`、`STATE.json` 永不触碰
- 路径 `resolve()` 后校验必须位于 `ai-agent/` 之下（防符号链接逃逸）
- 轮转用 `os.replace()` 同盘原子移动，不丢数据

**理由**
"一键"的诉求是**省事**，不是**放手**。dry-run 默认 + 范围硬限定 + 保护名单，
三者叠加才能在"好用"与"不会出事"之间站住。

**影响**
- 自动化定时清理需显式带 `--apply`
- 新增受治理目录时必须同步更新保护名单与范围校验

## ADR-005 · 只有 tmp/ 允许自动清理，主仓根禁止散落临时文件

**日期**：2026-09-19　**状态**：已采纳

**背景**
实测主仓根已堆积 **60+ 个** `_xxx.txt` / `_xxx.py` 临时文件（探针、构建日志、
一次性脚本），来源是历次开发中"随手写在根目录"。它们既无法判断是否过期，
也不敢贸然清理——**没有约定的临时区，就没有安全的清理边界**。

**决策**
- 一切中间产物**必须**落 `ai-agent/tmp/`（带 TTL，可被清理工具无条件清扫）
- 各业务模块若需临时文件，用各自模块的 tmp 子目录（如 `perf-analyzer/tmp/`），
  并纳入清理工具的治理范围
- **禁止**在项目根创建 `_xxx` 形式的散落文件

**理由**
"能不能自动清理"取决于"是否知道它是什么、属于谁、何时过期"。有约定的临时区
才有元数据，有元数据才敢清理。

**影响**
- 探针脚本改为落在模块 tmp 下，且**用完即删**（不留到下一轮）
- 存量散落文件需一次性归置（清理或归档），由 main 决定时机

## ADR-006 · AI 环节必须有硬预算，超时降级不阻断主链

**日期**：2026-09-19　**状态**：已采纳（事故沉淀）

**背景**
2026-09-19 实测：**资产定位**功能在控制台报「定位超时」。排查链路——
- LLM 模型链 `timeout=45s` × 2 模型 = 最坏 90s
- 画方（nad）准入检索：1588 台终端需翻 2 页，单请求超时 10s → 最坏 20s
- 二者叠加 → 逼近前端 25s 兜底
- 结果：**用户连平台/火绒的确定数据都看不到**（AI 只是三源之一，却拖垮了整条聚合）

> **2026-09-19 更正（结论不变，理由修正）**：原文写"服务是单线程，慢请求阻塞全局"
> **有误** —— 实测 `app.py:18/416` 用的是 `ThreadingHTTPServer` + `daemon_threads=True`，
> **每请求一线程**，慢请求并不阻塞其他请求。真正的要害是：
> **AI 与确定数据在同一个请求内串行** —— `run_ai_analysis` 先聚合上下文、再调 LLM、
> 最后一起返回，AI 慢则整个响应慢，确定数据被 AI 一并拖住。
> 所以"AI 必须有独立预算"的理由是**同请求内串行**，而非"阻塞全局"。

**决策**
1. 任何 LLM 调用的 `timeout` 与模型链长度**必须**计入预算，最坏耗时 ≤ 场景预算
2. 任何外部检索（第三方 API、跨网段请求）**必须**加**线程预算**收口
   （`_search_nad` 用 `threading + join(budget)` 硬收口）
3. AI 失败/超时一律**降级为 `available=false` + 原因**，确定数据照常返回
4. 交互式（P0）场景：**硬预算优先于完整度**

**理由**
AI 是**增益项**。让增益项阻断主链，是设计缺陷而非 AI 能力不足。
用户要的是"能看到确定数据 + 有 AI 补充更好"，不是"AI 不出来就什么都没有"。

**影响**
- 新增 AI 能力需在 `SKILL.md` 标注触发类型与预算等级
- 预算参数集中可配，便于按实测收紧（本次：LLM 8s/模型、画方 4s/请求 + 8s 线程预算）

## ADR-007 · 缓存/记忆写入失败时保留旧值，不写空

**日期**：2026-09-19　**状态**：已采纳（事故沉淀）

**背景**
同一次排查中发现：画方缓存 `nad_terminals_cached()` 在拉取失败时**写空缓存**
（`terms=None` + `ts=now`）。后果是——一次网络抖动 → 其后 5 分钟（TTL）内
**所有**读路径都拿不到画方数据，且不会重试。雪上加霜。

**决策**
- 拉取失败且**已有可用旧值** → **保留旧值**继续服务（按旧值服务优于无数据）
- 仅当**从未有过好数据**时才记录失败原因
- 同理适用于记忆写入：Skill 校验失败 → 拒绝写入，**不改动既有条目**

**理由**
"旧但可用"与"新但空"之间，前者对使用者价值更高。失败语义不该惩罚已有数据。

**影响**
- 缓存实现需区分"无数据"与"有旧数据但刷新失败"两种状态
- 需要配套的**数据新鲜度标注**（旧值要能让使用方知道它旧了）

## ADR-008 · 双服务对象与隐私边界

**日期**：2026-09-19　**状态**：已采纳

**背景**
初版 SOUL 把服务对象写成"运维人员"，属**范围窄化**。实测项目形态是双对象：

| 对象 | 位置 | 承载模块 |
|---|---|---|
| 桌面运维人员 | 中心控制台（多终端） | 终端监控、资产管理、策略下发、发布管理 |
| **终端使用人** | **客户端本机（单机）** | **磁盘清理、应用数据迁移、性能分析、网络排障、日志诊断、文件搜索** |

依据：主仓 README 明确写"**终端单机使用（推荐）——双击即用，无需配置、无需网络**"；
`disk_cleaner.py` / `appdata_scan.py` / `log_reader.py` 的使用者本来就是**使用人本人**。
用户亦明确要求："除桌面运维人员之外，还有电脑的使用人，帮助使用者完成终端的优化"。

**决策**
1. SOUL 身份扩为双对象，**明确两者诉求不同**（运维要批量定位异常，使用人要本机解决问题）
2. 新增准则四「对谁说话，用什么语言」—— 同一结论按受众分别表达（技术语言 vs 白话+动作）
3. 新增准则五「本机数据本机用」—— 隐私线划在**是否离开本机**，而非"是否接触"
4. 改造原「运维场景无小事」→ 准则六「越接近使用者本人，越要保守」
5. 长期目标按两类对象分列

**理由**

**① 隐私线必须划在"是否离开本机"，而不是"是否接触"。**
若照初版写"我不接触用户个人数据"，则 `file-search`（搜用户自己的文件）、
`disk-cleaner`（盘点微信/QQ 数据）**全部违规**——可它们正是使用人要用本机自己完成的。
正确的边界是：**本机判断可用，离机上报不可**。

**② 两类对象的利益可能冲突，必须显式处理。**
运维想看得更全（资产健康、合规），使用人未必愿意被看得太多（聊天文件、浏览历史）。
不显式划线，实现里就会默认"能上报就上报"——那是**产品事故，不是技术问题**。

**③ 使用人场景的误操作代价不可逆。**
运维批量操作有经验、有授权、有流程；使用人可能不懂，误删的是**他自己的数据**。
项目现有设计其实已体现这点（磁盘清理"仅定位与建议，不提供删除入口"、
迁移"移动而非删除"、"个人数据目录排除"），本 ADR 把它**从个别实现提炼为全局准则**。

**影响**
- 各模块接入时**必须**声明数据是否离机（Skill 的 `accepts` 与产出结构需标注）
- 上报字段需逐个过一遍"这算**结果**还是**内容**"的判断；判不准按"内容"处理
- 记忆层同样受约束（个人内容不因进记忆就可上报）
- 面向使用人的 Skill 默认「只分析不处理」，破坏性动作需强确认，优先"移动"而非"删除"

## ADR-009 · 超时预算按场景分级收紧（P0-1 / P0-2 修复）

**日期**：2026-09-19　**状态**：已采纳

**背景**
审计（`docs/AUDIT.md`）发现：ADR-006 定的"AI 必须有硬预算"，**5 套引擎只有 1 套落实**。
更深的问题是原配置里藏着一个**被忽视的隐性放大**：

| 引擎 | 原配置 | 真实最坏 | 说明 |
|---|---|---|---|
| 智能分析 | `timeout=60, max_retries=1` | **240s** | 单模型重试 1 次 = 2 次调用；两个模型 = **4 次** |
| 智能诊断 | `timeout=45, max_retries=0` | 90s | |
| IP 冲突 / 路由研判 | 复用分析链 | 240s | |
| 资产定位 | `timeout=8, max_retries=0` | 16s ✅ | 唯一合规（事故后修的） |
| 客户端个人版 | `urlopen(timeout=120)` | 120s | 使用人干等 2 分钟、无任何反馈 |

> **关键认知**：`max_retries` 与"模型链长度"是两个**独立相乘**的放大因子。
> 写超时的人往往只算了一层（"60s × 2 个模型 = 120s"），漏掉了重试那一层（→ 240s）。

**决策**
按**场景分级**定预算（不搞一刀切），并**统一 `max_retries=0`**：

| 引擎 | 场景 | 新配置 | 新最坏 | 依据 |
|---|---|---|---|---|
| 智能分析 | 控制台交互 | `timeout=10, retries=0` | **20s** | 实测 2.8s（SRV-055），留 3.5× 余量 |
| IP 冲突 / 路由研判 | 控制台交互 | 同上（复用链） | **20s** | 同上 |
| 智能诊断 | 终端推送 | `timeout=25, retries=0` | **50s** | 覆盖实测 11.3s 与极端 30.3s；契约 ≤120s |
| 资产定位 | 控制台交互 | `timeout=8, retries=0` | **16s** ✅ | 保持（已是合规样板） |
| 客户端个人版 | 使用人本机 | `urlopen(timeout=30)` | **30s** | 覆盖实测诊断区间 |

**为什么统一 `max_retries=0`**
重试的价值是"提高成功率"，代价是"**用户等待翻倍**"。而失败**已有备选模型兜底**，
重试用同一个模型再试一次属重复投入。对交互式场景（用户正盯着屏幕等），
**时间是首要约束**；失败后如实降级（`available=false` / 错误态），
比"多等一倍还不一定成功"更诚实。

**本次顺带更正一处早期错误认知**
原 ADR-006 写"服务是单线程，慢请求阻塞全局" —— **有误**。实测 `app.py:18/416`
是 `ThreadingHTTPServer` + `daemon_threads=True`，**每请求一线程**，慢请求不阻塞
其他请求。真正的要害是：**AI 与确定数据在同一个请求内串行**（先聚合、再调 LLM、
一起返回），AI 慢则确定数据被一并拖住。**结论不变**（AI 必须有独立预算），
但理由表述已修正——避免后来者基于错误认知做设计。

**影响**
- 各 Agent 配置 §6 预算段已同步（重新发布）
- 中心侧与客户端侧**同批收紧**（P0-1 + P0-2 一次修完，不留半截）
- ⏳ **未包含**：客户端使用人场景的**进度反馈**（"生成中…" + 可取消）。超时收紧了，
  但 30s 静默等待仍不理想，需改前端 —— 记为后续待办，不在本次超时修复范围
- ~~⏳ **未包含**：P0-3（面向使用人的 AI 仍用运维 prompt），需按准则四重写 prompt 内容~~
  → ✅ **已于 2026-09-20 完成**：个人版按准则四重写（保留证据可信性硬约束）；
  ⏳ 企业版仍待（它走中心链，需中心侧支持"受众"参数才能一并改）

## ADR-010 · 子仓并入主仓：去掉 gitlink，改为普通目录

**日期**：2026-09-21　**状态**：已采纳

**背景**
主仓以 gitlink（`160000 commit`）引用 8 个子目录：`server-platform`、`net-doctor`、
`file-search`、`perf-analyzer`、`disk-cleaner`、`log-inspector`、`desktop-policy`、`power-control`。

推送时发现：**这 8 个仓库从未配置远程**（`.git/config` 只有 `[core]` / `[user]`，
无任何历史 remote 痕迹）。后果是**远程主仓只存了指针** —— 任何人 clone 后，
这 8 个目录**全部为空**。而 `server-platform/server/` 是核心服务端代码。

**决策**
去掉 gitlink，将 8 个子仓的受控文件**并入主仓作为普通目录**。

**理由**
① **它们不是"独立发布单元"** —— 判据是内容：`server-platform` 同时住着服务端、
控制台、部署脚本，更像"工作区分割"而非可独立复用的库。
② **指针必须指向存在的仓库才有意义** —— 无远程的 gitlink 是"悬空指针"，
只会让 clone 残缺，不产生任何隔离收益。
③ **日后真需要独立发布再拆** 的成本，低于长期维护"半成品 submodule"的成本。

**执行（四步，每步可回退）**
1. **备份先行**：8 份 `.git` 全量 → `ai-agent/backup/subgit/`（2018 个对象）+ 导出提交历史；
   **实测**可从备份读出全部历史（`server-platform` 104 commits、`net-doctor` 48…）
2. `git rm --cached` 移除索引中的 8 个 gitlink
3. 移除子仓 `.git` 目录（否则 git 仍识别为 submodule）；迁移脚本带**前置校验**
   （备份不完整即中止），事后比对**工作区文件数零损失**（324→324、45→45…）
4. 按各子仓 `git ls-files` 清单**精确并入 222 个受控文件**（临时产物不吞进来）

**两个技术坑（已踩过，记录以免后人重踩）**
- **中文路径**：git 默认 `core.quotepath=true`，非 ASCII 路径被转义为 `\345\217\221…` 形式，
  经 shell 管道必失配 → 全程改用 **NUL 分隔**（`ls-files -z` / `--pathspec-file-nul`）。
- **忽略项致 add 整体失败**：主仓与子仓 `.gitignore` 会挡掉部分清单项使 `git add` 返回 1
