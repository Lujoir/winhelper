# AI 能力合规审计（2026-09-19 首次全量）

> 方法：拿 `soul/SOUL.md`（准则一~七）+ 五大模块规范 + ADR-001~008，逐条比对**代码实证**。
> 范围：全部 AI 能力（中心端 + 客户端）+ 数据上报链路 + 持久化/临时文件。
> 结论分级：✅ 合规 ｜ ⚠️ 部分合规 ｜ ❌ 违规或缺失

## 二、逐维度检查

### 准则二 / ADR-006：AI 必须有硬预算　❌ **5 套中只有 1 套落实**

| 能力 | 实测超时配置 | 最坏耗时 | 前端预算 | 判定 |
|---|---|---|---|---|
| 资产定位 | `timeout=8, max_retries=0` × 2 模型 | **16s** | 25s | ✅ 已收紧（2026-09-19 事故后修） |
| 智能诊断 | `timeout=45, max_retries=0` × 2 模型 | **90s** | 25s | ❌ **超预算 3.6 倍** |
| 智能分析 | `timeout=60, max_retries=1` × 2 模型 | **120s+**（含重试） | 25s | ❌ **超预算 4.8 倍** |
| IP 冲突 | 复用 `run_ai_analysis` 链 | 同上 120s+ | 25s | ❌ |
| 路由研判 | 复用 `run_ai_analysis` 链 | 同上 120s+ | 25s | ❌ |
| 客户端个人版 | **120s**（本机直连第三方） | **120s** | — | ❌ 使用人干等 2 分钟无反馈 |

> 证据：`api.py:3969`（timeout=60,max_retries=1）、`api.py:4114`（timeout=45）、
> `ai.py:996`（timeout=8，已修）；客户端 120s 见 CHRONICLE ADR-009 记载。
> **资产定位那次事故（ADR-006）的根因，在另外 4 套能力上原封不动地留着。**

### 准则五：本机数据本机用　⚠️ 行为合规，声明零散

| 检查 | 结果 |
|---|---|
| 上报字段是否含个人内容 | ✅ **不含**。`uplink.py:_asset_detail()` schema2 = `os/cpu/memory/disks/gpu/network/temps/machine/hostname`，全是硬件与系统元数据 |
| `_report_metrics()` | ✅ 性能指标，无个人内容 |
| 隐私声明是否写入 prompt | ❌ **6 套 prompt 中只有 1 套有**（`IPCONFLICT_SYSTEM_PROMPT` 末尾一行"证据仅含运维诊断数据，不涉及用户个人文件内容与任何凭据"） |
| 声明是否成为机制 | ❌ 是孤立的 prompt 文案，非可校验机制 |

> **判断**：**行为是对的，但没有保障**。目前靠"上传的恰好都是硬件数据"这一事实，
> 而非靠"机制不允许上传个人内容"。任何一次新功能扩展都可能打破它。

### 准则四：对谁说话，用什么语言　❌ 零落实

- 6 套 prompt **全部**是运维技术语言（"svchost"、"WHEA-Logger"、"准入登记"）
- 使用人场景（`disk-cleaner` / `perf-analyzer` / 客户端 AI）**没有任何面向使用人的表达规范**
- 违反证据：`_ND_AI_PROMPT_SYSTEM` 输出要求"【故障原因分析】引用日志依据（注明来自哪一类日志）"——
  要求模型输出**日志类别名**，这是给运维看的格式

### 模块 5：Soul 文件　❌ 完全缺失（但有可迁移的碎片）

- 无 Soul 文件；**6 套 prompt 各自定义身份**（"企业终端运维专家"×3 / "企业网络运维专家" /
  "资产管理助手" / "医院网络运维诊断专家"）
- **身份不一致**：中心端说"企业"，客户端说"医院"（而项目实际是**医院场景**：`llm.eye.ac.cn`、
  画方准入、VLAN 科室划分）→ **中心侧的"企业"反而写错了**
- 准则一（不虚构）**已有扎实实现**：各 prompt 都有"证据可信性硬约束"（只引用实际出现的事件 ID、
  必须附时间戳、缺失显式声明）→ 这部分**可直接升格为 Soul 准则一的实现样例** ✅

### 模块 1：记忆存储　⚠️ 只有碎片，无体系

| 现状 | 判定 |
|---|---|
| 中心端 `store.ai_insert()` 落库 | ⚠️ 那是**分析记录**（审计用途），非"记忆"（无提炼、无迭代、无跨会话复用） |
| 客户端 `/api/netdoctor/ai-history`（append/delete） | ✅ **最接近记忆**的东西，但**仅 netdoctor 有** |
| 模块级记忆目录 | ❌ 无 |
| 防串扰三道闸 | ⚠️ **有雏形**：`UPLINK_CONFIG_DIR` / `NETDOCTOR_CONFIG_DIR` 等 env 隔离，
  各模块配置分文件（`uplink_config.json` / `app_config.json`）→ **可平滑升级为 `MemoryScope`** |

### 模块 2：思维链与任务调度　❌ 缺失

- 无推理链落盘（`SESSION.jsonl` 之类的可追溯步骤记录）→ **无法回答"它当时凭什么这么判断"**
  （唯一例外：`ai.py` 的 `evidence`/`stats` 存证，那是**输入侧**存证，非**推理过程**）
- 无调度优先级定义（各调用点各自为政）
- **失败回退已有 2 层**：模型链降级 ✅（`llm_chat_chain`）、阶段降级 ✅（资产定位 `available=false`）；
  **第 3 层（任务级重试/重排/放弃留痕）缺失**

### 模块 3：上下文与日志治理　❌ 缺失

- 上下文：中心端 `ai_records` 落库 ✅，但**保留策略未见**
- 客户端 AI 历史：有 append/delete ✅，但**无 TTL、无容量上限**（需确认）
- 临时文件：**主仓根 60+ 个 `_*.txt` / `_*.py`**（实测）→ ADR-005 已定规范，各模块**尚未接入**
- 无一键清理（`ai-agent/tools/cleanup.py` 已就绪，但无模块接入）

### 模块 4：Skill 校验　⚠️ 有实质能力，但未收口为机制

| 已有 | 判定 |
|---|---|
| 预算分配 `_allocate_diag_budgets` | ✅ 可复用为 Skill 的输入限幅 |
| 结构感知截断 `truncate_text` / `_clip_json_*` | ✅ |
| 乱码探测 `_detect_mojibake` | ⚠️ **仅用于"存证标记"，未用于"写入把关"** |
| 输入 schema 校验 | ❌ 各 `build_*_context` 自行处理，无统一 schema |
| 输出 schema 校验 | ❌ LLM 返回文本**直接落库**，无结构校验 |
| 无关内容判定 + 回执 | ❌ 无 |

## 三、问题清单（按优先级）

### P0 — 有实际风险

| # | 问题 | 影响 | 状态 |
|---|---|---|---|
| **P0-1** | 中心端 4 套能力预算超标（真实最坏 **240s** / 90s vs 前端 25s） | **用户等不到结果**（资产定位事故会在分析/诊断上重演） | ✅ **已修**（ADR-009）：分析 10s×2=20s、诊断 25s×2=50s、`max_retries` 统一归零 |
| **P0-2** | 客户端个人版 AI `timeout=120` | 使用人干等 2 分钟、无任何反馈 | ✅ **已修**（ADR-009）：120s → 30s；⏳ 进度反馈待做 |
| **P0-3** | 面向使用人的 AI 用运维 prompt（"医院网络运维诊断专家"） | **答非所问**：使用人看不懂 | ⏳ **待办**（需按准则四重写 prompt 内容） |

> **修复过程顺带更正一处错误认知**：原文依据"服务是单线程、慢请求阻塞全局" ——
> 实测 `app.py:18/416` 是 `ThreadingHTTPServer`（每请求一线程）。真正的要害是
> **AI 与确定数据在同一请求内串行**。结论不变，理由已更正（见 ADR-006 补注 / ADR-009）。
>
> **另发现一处测试盲区并已补门禁**：`run_ai_analysis` 的超时改动原本**无任何测试覆盖**
> （`test_ai_ipconflict.py` 的 mock 未记录 `timeout`）。已补两条断言固化
> `timeout=10 / retries=0` 与"双模型最坏 ≤ 场景预算"，防止日后被改回去无人发现。

## 四、做对了的（不要推翻重做）

| # | 项 | 证据 |
|---|---|---|
| A | **上报字段只含硬件/系统元数据** | `_asset_detail()` schema 2 |
| B | **模块配置目录已隔离** | `UPLINK_CONFIG_DIR` / `NETDOCTOR_CONFIG_DIR` / filesearch 独立子目录 |
| C | **证据存证 + 预算治理成熟** | ADR-027（`build_diagnose_context` 返回 prompt/evidence/stats 三元） |
| D | **证据可信性硬约束**已在各 prompt 落地 | "只引用实际出现的事件 ID + 必附时间戳 + 缺失显式声明" |
| E | **模型链降级**已实现 | `llm_chat_chain` + `can_fallback` 判定 |
| F | **降级契约**已实现 | 资产定位 `available=false`，确定数据照常返回 |
| G | **凭据不入 exe** | 一律运行时读配置（README 铁律） |
| H | **客户端 AI 历史有增删能力** | `/api/netdoctor/ai-history-append/-delete` |

> **结论：项目底子比表面看起来好**。不是"从零建"，而是"把已有的好实践收口成机制"——
> 存证、预算、证据约束、降级契约都已存在，缺的是**统一入口、统一声明、统一校验**。
