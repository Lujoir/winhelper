## 已有基础（升级而来，不是从零建）

本项目原来的 `ai_history.jsonl`（`_records_dir()/`）是**全项目最接近"记忆"的一处**：

- ✅ JSONL 追加（崩溃安全 + 可回放）
- ✅ 原子写（tmp + `os.replace`）
- ✅ 200 条滚动上限
- ✅ 增 / 删（`-append` / `-delete`）
- ❌ 但**无物理边界校验**（任何代码都能写别的模块）
- ❌ **无归档**（超限直接丢弃最旧，历史不可追溯）
- ❌ 记录**不带来源标**（无法分辨归属）

`MemoryScope` 把前三条保留、后三条补上。

## 长期记忆（经验沉淀）

### M-001 · 使用人视角是硬要求，不是措辞偏好
**教训来源**：P0-3。`_ND_AI_PROMPT_SYSTEM` 原为"你是医院网络运维诊断专家"，
输出要求"注明来自哪一类日志" —— 而本引擎的主要入口是**使用人本机自用**。
使用人拿到一份满是日志类别名的运维报告，等于没给结论。

**固化**：本模块输出必须满足「问题是什么 → 我做了什么判断 → 你现在该做什么」
三段式；技术细节保留但降为支撑材料。

### M-002 · 等待必须有反馈
**教训来源**：ADR-009。原 `urlopen(timeout=120)`，使用人点一下"AI 诊断"干等两分钟、
无任何进度提示。运维场景尚有"任务在跑"的心理预期，**使用人没有**。

**固化**：超时上限 30s；且必须有"生成中…"提示（此项仍待做）。

### M-003 · 数据去向必须让使用人知道
**教训来源**：SOUL 准则五。个人版会把本机网络数据发往**第三方 LLM**，
用的是**使用人自己的 API Key**。他有知情权。

**固化**：发起请求前显式告知"将把哪些数据发往哪个服务"（此项仍待做）。

## 边界（本模块记忆不得包含）

依 SOUL 准则五（本机数据本机用）：

- ❌ 使用人的个人文件内容、聊天记录、浏览历史
- ❌ 明文凭据（API Key 只记录"已配置/未配置"，不记录值）
- ❌ 任何可用于识别个人身份的信息（除非使用人主动提供）
